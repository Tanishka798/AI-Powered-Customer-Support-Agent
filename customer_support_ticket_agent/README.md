# Customer Support Ticket Agent

A support agent you can type or speak to. It answers policy questions from a small knowledge base using retrieval-augmented generation (RAG), and collects details over several turns to open support tickets. Any agent reply can be played back as speech. It uses FastAPI, Streamlit, LangGraph, Chroma, and an open-source LLM behind an OpenAI-compatible endpoint, with local Whisper speech-to-text and Edge TTS.

## Architecture

```text
Streamlit (streamlit_app.py)
  └─ src/ui/api_client.py ───HTTP──> FastAPI (src/api/server.py)
                                        ├─ POST /chat ─> SupportPipeline (src/pipeline.py)
                                        │                 └─ LangGraph workflow (src/llm/workflow.py)
                                        │                      retrieve ─> decide ─┬─> greeting
                                        │                                          ├─> answer
                                        │                                          ├─> clarify
                                        │                                          ├─> ticket
                                        │                                          └─> ticket lookup
                                        └─ /voice/* ──> VoicePipeline (src/voice/pipeline.py)
                                                          ├─ STT: FasterWhisperSTT
                                                          └─ TTS: EdgeTTS
```

Voice sits beside the agent, never inside it:

```text
Mic in the chat box -> POST /voice/transcribe -> transcript placed in the chat box -> [Enter] -> POST /chat (unchanged)
Agent reply -> 🔊 click -> POST /voice/synthesize -> audio player under that reply
```

Each customer turn runs through four graph nodes:

1. **retrieve**: searches the Chroma knowledge base for relevant policy chunks.
2. **decide**: the LLM returns a small JSON decision (`greeting`, `answer`, `clarify`, `ticket`, or `ticket_lookup`) and any ticket fields stated in this message. A short standalone greeting is routed directly to greeting generation. The ticket collector validates every supplied field before storing it.
3. **greeting / answer / clarify**: greetings and clarifications are generated by the configured LLM; FAQ answers use retrieved knowledge chunks and list their source files. Follow-up turns include bounded conversation history. If an FAQ has no relevant evidence, the agent says so instead of guessing.
4. **ticket**: stores valid fields, asks for the next missing one, rejects malformed email values with a correction prompt, and creates the ticket once everything validates. Each session gets at most one ticket.
5. **ticket_lookup**: reads the existing ticket record and reports its actual status.

A policy question asked partway through a ticket is answered, followed by a reminder of the pending ticket question.

## Provider choices

| Concern | Default | Why |
|---|---|---|
| LLM | `qwen2.5:3b` via [Ollama](https://ollama.com) at `http://localhost:11434/v1` | Small, open-source, runs locally, OpenAI-compatible API |
| Embeddings | `sentence-transformers/all-MiniLM-L6-v2` | Small and fast; downloaded once on first start |
| Vector store | Chroma, stored in `.data/vector_db` | Local and file-based; chunks have stable IDs, so restarts don't add duplicates |
| Speech-to-text | [faster-whisper](https://github.com/SYSTRAN/faster-whisper) `base.en`, CPU, int8 | Runs locally, so recordings never leave the machine and no API key is needed; decodes browser WAV/WebM and other formats itself; transcribes a short request in about a second on CPU |
| Text-to-speech | [Edge TTS](https://github.com/rany2/edge-tts), voice `en-US-AriaNeural` | Natural neural voices, fast, free, and no API key; the trade-off is that it needs internet access |

Any OpenAI-compatible endpoint serving an open-source model works, such as vLLM, LM Studio, or llama.cpp server. Set `LLM_BASE_URL`, `LLM_MODEL`, and `LLM_API_KEY` in `.env`.

Voice is configured with `STT_MODEL` (for example `small.en` for better accuracy), `STT_DEVICE` (`cuda` with a supported GPU), `STT_COMPUTE_TYPE`, `STT_LANGUAGE`, and `TTS_VOICE` (run `edge-tts --list-voices` for options). Both adapters implement the supplied `STTService`/`TTSService` contracts, so another allowed provider can be swapped in by changing `src/voice/factory.py`. No end-to-end conversational platform is used.

Retrieval returns up to `RAG_TOP_K` chunks. Chunks with a Chroma distance above `KnowledgeRetriever.RELEVANCE_THRESHOLD` (1.0) are dropped, which is how unknown questions end up with no answer instead of an invented one.

## Requirements

- Python 3.11 or newer.
- An OpenAI-compatible endpoint serving an open-source instruction model (for the defaults: Ollama plus `ollama pull qwen2.5:3b`).
- Internet access on first start to download the embedding and Whisper models (about 240 MB together), and whenever a reply is played back (Edge TTS).
- A browser with microphone access. Browsers only allow the microphone on `localhost` or HTTPS.

## Setup

### Quick start (recommended)

Install [Ollama](https://ollama.com/download) and start it, then, from the project root:

```sh
python scripts/setup.py          # Windows: py -3.11 scripts\setup.py
```

The script only installs or downloads what's missing, so it's safe to re-run:

| Step | What it does |
|---|---|
| Virtual environment | Creates `.venv` if it doesn't exist |
| Dependencies | Installs `requirements.txt` with CPU-only PyTorch, which only runs the small embedding model; the CUDA build would add several GB |
| Configuration | Copies `.env.example` to `.env` if there's no `.env` |
| Models | Downloads the embedding model and Whisper model into the Hugging Face cache (about 240 MB, once) |
| LLM | If Ollama is running and `qwen2.5:3b` is missing, pulls it through Ollama's API (about 1.9 GB, once) |

Options: `--skip-models` (download models on first start instead), `--gpu` (install the CUDA PyTorch build).

Nothing heavy ships with the project. The models are downloaded on first use, the vector index in `.data/` is rebuilt on first start, and the API checks for the LLM at startup and pulls it from Ollama if it's missing (turn this off with `LLM_AUTO_PULL=false`).

### Manual setup

Linux / macOS:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
cp .env.example .env
ollama pull qwen2.5:3b
```

Windows PowerShell:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
Copy-Item .env.example .env
ollama pull qwen2.5:3b
```

Edit `.env` to point at a different model endpoint. Don't commit credentials.

## Run

Start the API, then the UI in a second terminal. Run both from the project root.

Linux / macOS:

```sh
uvicorn src.api.server:app --reload --host "${API_HOST:-127.0.0.1}" --port "${API_PORT:-8000}"
streamlit run streamlit_app.py --server.address "${STREAMLIT_HOST:-127.0.0.1}" --server.port "${STREAMLIT_PORT:-8501}"
```

Windows PowerShell (the `${VAR:-default}` syntax is POSIX-only, so pass values directly):

```powershell
uvicorn src.api.server:app --reload --host 127.0.0.1 --port 8000
streamlit run streamlit_app.py --server.address 127.0.0.1 --server.port 8501
```

The UI is at `http://localhost:8501`, and the API docs are at `http://localhost:8000/docs`. To check a ticket, enter its ID in the **Look up ticket** box in the Streamlit sidebar, or open `http://localhost:8000/tickets/<ticket_id>`.

### API

| Endpoint | Purpose |
|---|---|
| `GET /health` | `200 {"status": "ready"}` once startup has finished, otherwise `503` |
| `POST /chat` | `{"session_id", "message"}` → `{"success", "session_id", "response", "sources", "ticket_id"}` |
| `GET /tickets` | Every stored ticket, in creation order |
| `GET /tickets/{ticket_id}` | The stored ticket, or `404` |
| `POST /voice/transcribe` | Multipart `audio` file → `{"success": true, "transcript", "processing_time_ms"}` |
| `POST /voice/synthesize` | `{"message_id", "text"}` → `audio/mpeg` bytes, with `X-Message-Id` and `X-Processing-Time-Ms` headers |

```sh
curl http://localhost:8000/health

curl -X POST http://localhost:8000/chat \
  -H 'Content-Type: application/json' \
  -d '{"session_id":"demo-1","message":"How long does standard shipping take?"}'
```

On Windows PowerShell, use `Invoke-RestMethod` or the `/docs` page.

Error responses: `422` for an invalid request body, `503` when a component isn't ready, `502` when the agent fails. The `502` message is generic; the details are logged on the server only.

Voice errors use `{"success": false, "error": "..."}`: `422` for empty, unsupported, unreadable, or speech-free audio and blank text; `413` for recordings over 10 MB; `502` for provider failures; `503` if voice failed to start. If voice fails at startup, the API still starts and typed chat keeps working.

```sh
curl -X POST http://localhost:8000/voice/transcribe -F "audio=@recording.wav;type=audio/wav"

curl -X POST http://localhost:8000/voice/synthesize \
  -H 'Content-Type: application/json' \
  -d '{"message_id":"m1","text":"Ticket CST-2026-0001 has been created."}' -o reply.mp3
```

### Using voice in the UI

1. Tap the **mic** inside the chat box. While you record, the box shows a live waveform instead of the text field. Approve the recording (✓) to transcribe it, or cancel (✕).
2. A spinner shows while it transcribes. The transcript then appears **in the same chat box**, with a note to check it.
3. Edit it if needed and press **Enter** to send, or clear it. Nothing reaches the agent until you press Enter, and it goes through the normal chat, so sessions, answers, and tickets work exactly as with typing.
4. Click **🔊** under any agent reply to hear it. Audio is generated only on click, then cached for that reply, and only the selected reply's player is shown. Speaker buttons are disabled while audio is being generated. If playback fails, a warning appears under that reply and the text stays.

## Troubleshooting

| Symptom | Likely cause and fix |
|---|---|
| API won't start: "Failed to initialize support knowledge base" | The embedding model couldn't download (no internet on first run), or `knowledge_base/` is missing. |
| `/chat` returns 502 for every message | The LLM endpoint is unreachable or the model isn't pulled. Check that Ollama is running and `LLM_BASE_URL` is right, then restart the API (it pulls a missing model automatically) or run `ollama pull qwen2.5:3b`. The API log shows the real error. |
| Frequent 502s mentioning an "invalid routing response" in the logs | The model isn't returning valid JSON. Try a larger or more instruction-following model. |
| Answers use old or deleted policy text | Indexing only adds new chunks. Delete `.data/vector_db` and restart after editing or removing documents. |
| Errors after changing `EMBEDDING_MODEL` | The stored vectors have the old dimensions. Delete `.data/vector_db` and restart. |
| UI says it can't connect to the backend | The API isn't running, or it's on a different address. Streamlit reads `API_BASE_URL` from the environment, not from `.env`, so export it in the shell that runs Streamlit. |
| Sessions or tickets disappear | Both are stored in memory and reset when the API restarts (including `--reload` restarts). |
| Voice endpoints return 503 | Voice failed to start, usually because the Whisper model couldn't download. Check the API log for "Voice pipeline failed to start". Typed chat still works. |
| Microphone button does nothing or is blocked | Allow microphone access in the browser. It must be opened on `localhost` or over HTTPS. |
| 🔊 shows "Couldn't play this response" | Edge TTS needs internet access. Check the connection and click again; the text reply is unaffected. |
| Transcripts are inaccurate | Use a larger model, such as `STT_MODEL=small.en`, or `STT_DEVICE=cuda` on a supported GPU. |

## Limitations

- Sessions and tickets live in memory only, which suits a single-process demo, not production.
- Chroma search and embedding run synchronously inside async handlers, so heavy concurrent load will block the event loop. Whisper transcription runs in a worker thread.
- Edge TTS is an online service. Use a local TTS adapter, such as Piper or Coqui, for offline use.
